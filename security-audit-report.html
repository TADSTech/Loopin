Loopin v3 — Security Audit & Hardening

Pre-launch review of the SaaS codebase (Next.js 16 · Supabase · Bachs payments · Google Calendar)

Date: 2026-10-16 Scope: auth · RLS · API · payments · config · deps Posture: remediated + residual items listed Build ✓ · TypeScript ✓ · ESLint ✓ · 80 tests ✓

Executive summary

A focused white-box review of the Loopin v3 codebase surfaced 6 security issues (2 high/medium, 4 medium/low) plus a set of hardening gaps appropriate for a SaaS about to go live. The most serious was a stored cross-site scripting (XSS) sink on the public event pages and an open redirect in the OAuth callback. Both are now fixed. The authentication model (Supabase RLS) is, on the whole, well constructed: the entitlement and secret tables are correctly locked down so that only the server (service-role) key can write them, and users cannot forge plan upgrades.

All fixes have been applied, type-checked, linted, and the production build passes. The remaining items in the Go-live checklist are operational (secrets hygiene, CSP tightening) rather than code defects.

Findings

High Stored XSS via JSON-LD dangerouslySetInnerHTML Fixed
app/e/[slug]/page.tsx · app/about/page.tsx · app/components/structured-data.tsx

Three pages inject JSON.stringify(...) directly into a <script type="application/ld+json"> via dangerouslySetInnerHTML. JSON.stringify does not escape </script>, so a published event whose title, notes, or location contains </script><script>alert(1)</script> breaks out of the script tag and executes in every visitor's browser. The public event page is indexable, so this is a stored, worm-able XSS.

Fix: added lib/json-ld.ts · safeJsonLdStringify() which escapes <, >, &, U+2028 and U+2029 to their Unicode escapes, and routed all three sinks through it.

High Open redirect in OAuth callback (next param) Fixed
app/auth/callback/route.ts

The post-login redirect target was taken straight from ?next= and concatenated onto the origin: NextResponse.redirect(\`${origin}${next}\`). An attacker who controls the callback URL can set ?next=//evil.example (protocol-relative) or an absolute URL to bounce a freshly-authenticated user to a phishing site that impersonates Loopin — a classic credential-harvesting vector.

Fix: added isValidLocalRedirect() — only paths beginning with a single / (not // or /\) that resolve to the same origin are accepted; everything else falls back to /.

Medium Missing HTTP security headers (CSP / HSTS / X-Frame-Options) Fixed
next.config.ts

The app sent no Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, or Strict-Transport-Security. This leaves users exposed to clickjacking, MIME sniffing and weakens XSS containment.

Fix: added an async headers() block applying a restrictive baseline CSP (default-src 'self', frame-ancestors 'none', base-uri 'self', object-src 'none', connect-src limited to *.supabase.co), HSTS (preload), and the remaining headers above.

The CSP keeps 'unsafe-inline' for scripts because the Next.js App Router emits inline RSC bootstrap scripts. For a fully strict policy, move to a per-request nonce via middleware — tracked as a follow-up.

Medium No rate limiting on paid AI endpoints (cost / DoS abuse) Fixed
app/api/v1/extract/route.ts · app/api/checkout/route.ts · lib/rate-limit.ts

The public extraction API and the checkout endpoint had no throttling. Each successful extraction call spends real money on Groq/OpenRouter tokens, so an attacker with a valid key (or a leaked key) could drain the AI budget, and the checkout endpoint could be used to spam Bachs session creation.

Fix: added lib/rate-limit.ts (fixed-window limiter) and wired it in: extraction is capped at 30 req/min per key+IP, checkout at 10 req/min per user, returning 429 with a Retry-After header.

In-memory limiting is per serverless instance. Before heavy production traffic, back it with a shared store (Upstash Redis / Vercel KV) using the same keys.

Medium Cron secret accepted in URL query + fail-open behaviour Fixed
app/api/cron/reminders/route.ts

The scheduled reminder processor accepted the CRON_SECRET via a ?secret= query parameter (logged in every proxy/access log) and, more dangerously, skipped the check entirely when the secret was unset — letting anyone trigger reminder processing if the env var was missing.

Fix: removed the query-string path, now requires Authorization: Bearer only, and fails closed (HTTP 503) when CRON_SECRET is not configured.

Low Webhook delivery — SSRF surface & unbounded timeout Fixed
lib/webhooks.ts · app/platform-actions.ts

User-registered webhooks were delivered with no timeout and no host validation. A logged-in user could target internal services or the cloud metadata endpoint (169.254.169.254) — a blind SSRF — and a slow endpoint could stall the caller request.

Fix: added isSsrfSafeTarget() (rejects loopback, RFC1918, link-local/metadata and IPv6 unique-local ranges) enforced at both registration and delivery, plus a 5s per-delivery AbortController timeout.

Low Unbounded upload size in extraction Fixed
app/actions.ts (ingestEvents)

Image uploads were only checked for size > 0 (capped overall by the 10 MB server-action limit). Added a per-file ≤ 10 MB cap.

Phase 2 — Rate-limit UX, IP banning & 404

Building on the throttling above, the abuse path now has a full lifecycle: warn, then escalate, then enforce.

Escalating rate limiter → IP ban

lib/rate-limit.ts now records a strike on every blocked request, keyed on the client IP. Reaching the threshold inside the window escalates to an IP ban. Thresholds are env-tunable: RATE_STRIKE_THRESHOLD (default 8), RATE_STRIKE_WINDOW_MS (10 min), RATE_BAN_DURATION_MS (15 min).

Bans are enforced app-wide by the middleware (proxy.ts): a banned IP gets a 403 "Access temporarily blocked" page on every request, so a caller can't bypass a limit by reloading pages or switching endpoints. The strike is keyed on the client IP from lib/ip.ts (x-forwarded-for first hop → x-real-ip).

In-app warning modal

When the on-page extractor is rate-limited or banned, the server action returns an abuse flag (lib/event-types.ts) and the home page raises the new app/components/warning-modal.tsx — a friendly "slow down"/"access paused" dialog with a retry countdown and a support link. It's dismiss-aware: it re-appears only for a fresh block.

Custom 404 page

app/not-found.tsx provides a branded 404 (also used for missing public event pages) that returns users to the app instead of the default Next.js error screen.

The limiter is still in-memory (per serverless instance) and keys bans on IP. Before heavy production traffic, back it with a shared store (Upstash Redis / Vercel KV) so bans and counters hold across instances. Tighten RATE_STRIKE_THRESHOLD for a stricter policy.

What's already done well (verified)

  • RLS lockdown of secrets & entitlements. calendar_tokens has RLS enabled with no policies (only the service-role key can touch it), and subscriptions has only a SELECT policy — plan upgrades can only be written by the payment webhook via the admin client. A normal user cannot forge Pro.
  • Server-side trial eligibility. never-subscribed + unused-device is re-checked at checkout; a missing trial product returns 503 rather than silently charging.
  • Webhook signature verification. Bachs signatures use HMAC-SHA256 with a constant-time compare and a 5-minute replay window; raw body is verified before parsing.
  • API keys hashed at rest. Only a SHA-256 hash + short prefix are stored; the plaintext is shown once.
  • No committed secrets. .env* is gitignored and no live keys were found in the tree.
  • Workspace membership enforced by RLS via SECURITY DEFINER helpers (the earlier 42P17 recursion is fixed).

Go-live checklist (residual / operational)

  • Rotate and confirm all production secrets on Vercel are byte-identical to Bachs' webhook signing secret (per AGENTS.md §6); verify the webhook lands with event source → Account events.
  • Revoke the temporary Supabase PAT mentioned in SETUP.md Step 1 (sbp_fca34…).
  • Confirm .env is never committed (it is gitignored) and that Vercel env uses encrypted storage.
  • Enable Supabase "Prevent use of leaked passwords" (HaveIBeenPwned) — optional but recommended (SETUP.md §Optional).
  • Back the rate limiter with a shared store (Upstash/Redis) before scaling traffic.
  • Replace the CSP 'unsafe-inline' script allowance with a per-request nonce (middleware) for a strict policy.
  • Add full SSRF protection that resolves DNS and inspects the resolved IP (the current guard is hostname-based).
  • Run npm audit / Dependabot on the dependency tree and keep Next.js + Supabase SDKs patched.
  • Add monitoring/alerting on the Bachs webhook [bachs-webhook] logs and on 429/401 spikes.
